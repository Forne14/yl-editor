Field groups

#44 · Chrome: group close plain fields in one outline (no overlapping dashed outlines). Prototype for approval, 2026-11-28.

Your rule from 2026-11-11: no overlapping dashed outlines. Lists already follow it (#28): one outline, thin dashed lines between items and fields. Plain fields outside lists still get one outline each, and on the demo page those cross. This page proposes the same treatment for plain fields and asks four rulings, listed at the end. Everything below is live: hover, click and Tab through the fields.

  • The group's outline is the list frame: the same dashed border and the same 12px padding (--cms-list-pad). Lines run halfway between neighbouring fields, across the whole outline, so a facts row's line also passes under its label.
  • The axis is read from the boxes, as for lists: fields stacked get horizontal lines, fields side by side get vertical ones (the byline in section 2), a wrapping row gets both.

3 · Ruling G1: how a group is declared

A · A wrapper attributeRecommended

The host marks the element that holds the fields. Every field inside it (not inside a list) is one group. 

<section data-edit-group>
  <h2 ${attrs(about("title"))}>…</h2>
  <p ${attrs(about("body"))}>…</p>
</section>
// or ${attrs(editable.group())}
  • Predictable: the outline is where the host put it, at every width.
  • New public surface: data-edit-group and a helper on editable().
  • A host that forgets it gets today's crossing outlines, so A comes with the warning below.

B · Found from proximity

The chrome groups any fields whose outlines would touch or cross, and draws one frame around their union.

  • No host work.
  • Groups change with the layout: drag the corner of the box below. Wide, the author and date have an outline each; narrow enough to wrap, they join and a frame appears around them.
  • The union of two far-apart fields can cover markup of the host that isn't editable (an image, a button) and the frame can cross a list's frame.

C · Attribute, plus a warning

A, and on mount the chrome checks the outlines of fields left ungrouped. When two would cross, console.warn names both fields and suggests data-edit-group. Nothing on screen changes. 

[yl-editor] Outlines of
"pages/home/title" and
"pages/home/lede" cross.
Wrap them in an element
with data-edit-group.
  • The host finds the problem in development, as with an unkeyed list item today.
  • Checked once per mount and on resize; no layout cost while editing.

Recommended as A + C together: an explicit attribute, and the warning so nobody ships crossing outlines by accident.

4 · Ruling G2: does a group carry a tag?

Lists have a tag on their top edge ("Artists · 3 of 6"). A group has no count.

A · No tag; each field keeps its badgeRecommended

Hovering or focusing a field shows its badge, as today. The frame says "these belong together"; the badge says which one you're on. No new text. The badge sits just above its field, so it covers the line above it, as it does in a list item today.

B · A tag when the host names the group

editable.group({ label: "About" }) puts a tag on the top edge, like a list. Unnamed groups have none. Field badges still show on hover. Two labels can be on screen at once.

5 · Ruling G3: a locked field inside a group

A group can hold fields of several documents (a heading from pages/home, a footer line from settings/site), so one field can be locked while the others aren't. Today a locked field's outline is muted.

A · Frame stays accent; the locked field is markedRecommended

The frame is muted only when every field in it is locked. A locked field shows a thin muted dashed outline on hover and its muted badge with the reason, as today. Clicking it shows the reason as a toast.

B · Locked fields are never grouped

The chrome leaves a locked field out of its group and gives it its own muted outline. Simpler to read, but the muted outline is back next to the group's and they can cross, which is what the ticket removes.

6 · Ruling G4: groups and lists

A · A list is never inside a groupRecommended

Fields inside a data-edit-list belong to the list, never to a group around it. A group that wraps a list keeps only its own plain fields, and its lines stop at the list's frame rather than crossing it. If that leaves one field, it's drawn as a plain field. Nested groups: the innermost wins, and console.warn says so.

B · A group may wrap a list

The list's frame is drawn inside the group's frame. That is a dashed outline inside a dashed outline: the nesting #28 ruled out (D1).

Rulings asked

G1 How a group is declared. Recommended: A + C, a data-edit-group wrapper (editable.group()) plus a console.warn when ungrouped outlines cross.
G2 Group tag. Recommended: A, no tag; field badges as today. No new chrome text.
G3 Locked field in a group. Recommended: A, it stays in the group; frame muted only when all fields are locked.
G4 Groups and lists. Recommended: A, list fields never join a group; innermost group wins.

Not changing: fields outside a group, list frames, the badge, keyboard order (Tab still visits each field in page order; the group adds no stop), and the CSP rule (positions only through custom properties).
