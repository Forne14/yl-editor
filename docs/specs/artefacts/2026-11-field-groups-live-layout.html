Groups and live layout

#44 · Chrome: group close plain fields in one outline (no overlapping dashed outlines). PR #54. A decision for Yassine, 2026-11-28, after review round 3.

Where it stands

The groups look and work as approved (G1–G11). Three review rounds found 9, 6 and 7 problems, all real. Round 3 still has three important ones, so by your rule the design is the question, not the code.

Round Findings What kind
1 9 Lifecycle (Discard left a frame), measuring (borders, pad 0), warnings scope
2 6 Measuring CSS values in JS (rem pads, inline wrappers), measured before the class applied
3 7 A wrapper that turns display: contents at a breakpoint; host CSS on .cms-group hiding a member makes the group draw and retire every frame (a loop); a group wrapping list items; Discard-deleted fields rejoin after Done → Edit

The pattern. About half of the 22 findings share one cause: the chrome works out which fields are in a group from the live page, on every repaint. It counts only fields that have a box right now, re-reads the wrapper's display, and redraws when a field appears or vanishes. That makes groups respond to the host's CSS, media queries and its own class, and every round finds a new way those interact. The rule that drives it, "a group with fewer than two fields shown draws nothing", was mine (round 1), not one of your rulings.

The options

A · Keep it live (today)

Membership and the inline check are worked out from the rendered page on every paint.

For the editor

  • A group whose second field is hidden at this width looks like a plain field.

For the site developer

  • Nothing to learn: any CSS works, in theory.
  • In practice each combination (breakpoints, class-keyed rules, hidden fields) is a new edge, and the round 3 loop shows they can fight. Expect more rounds.

B · Decide once, from the markupRecommended

Which fields form a group is decided when the chrome scans the page (and after a list swap or refresh): the fields inside the wrapper, not inside a list, whose document the editor can still see. Layout never changes membership. Repainting only places the frame and lines.

For the editor

  • A group always looks like a group, even when one field is hidden at this width: the frame goes around the wrapper, with no line next to a field that has no box.
  • A field of a document Discard deleted leaves its group for good (it leaves the editor too).

For the site developer

  • One documented rule: the wrapper is block-level (or inline-block) in edit mode. Checked at scan; a wrapper that is inline or contents then is ignored with the warning (G11). Changing it later at a breakpoint is unsupported, and the docs say so.
  • Fixes the round 3 loop and the breakpoint and Discard findings by construction; the list-items one is a one-line scan check.

C · CSS outline only, no lines

The chrome only adds cms-group to the wrapper. CSS draws the frame as the wrapper's own outline; there are no separators, so no geometry code at all.

For the editor

  • Changes the approved look: no line between fields, so it's harder to tell where one field ends. Hover still shows each field's box.

For the site developer

  • Simplest and sturdiest. Still needs the block-level rule.
  • Lists keep their lines, so groups and lists would look different.

Recommendation

B. It keeps the approved look and every ruling, removes the cause of the recurring findings instead of patching each one, and gives the site developer one rule to follow instead of an unknown set of CSS interactions. The cost is one visible change: a group with a field hidden at some width keeps its frame.

Either way, the four round 3 nits (the list :last-child doc line, a right-border comment, the watch releasing nodes after Done, and the Discard doc line) are plain fixes and go in the same push.
