Media widget and MediaStore reshape (#3)

Issue #3 (Media: reshape MediaStore and ship a default media widget). This page proposes the default media widget, drawn with the real chrome tokens and classes, the reshaped MediaStore seam and its wire, and the host contract. Nothing here is ruled: every Recommended is a proposal for Yassine to accept or overrule, and the open points are listed at the end. All on-screen text is proposed copy, keyed for src/chrome/strings.ts (§4).

Approved 2026-11-28 · not built
Theme
The switch forces the chrome tokens; the shipped chrome follows the OS setting.

0 · The proposal in one screen

  1. Widget. A popover (bottom sheet under 40em) with one Choose file button inside a drop target, paste support, a native <progress>, a preview, an alt text input and a Decorative checkbox. Done and Cancel as everywhere else.
  2. Value. The field stores { id, alt }, or { id, alt: "", decorative: true }, or null. Alt text is content: it is drafted, published and revisioned with the page.
  3. When it saves. The value is committed only once the media is ready (stored, with a preview). An upload or job in progress is not a change yet: leaving the popover lets it go on and saves it when it is ready; Esc or Cancel upload stops it and saves nothing.
  4. Store. upload takes a ReadableStream, answers ready or processing + job id; job(id) reports progress; resolve is batched and returns a host-shaped variants plus a package-shaped render (HTML's own src/srcset/<source type> vocabulary), which is all the chrome reads.
  5. Wire. An opt-in media option on createContentHandlers adds POST media (raw body), GET media?ids= and GET media-job (+ optional DELETE), behind the same CSRF guard, gated by canEdit on the document the field belongs to.
  6. Host markup. A media field is an <img>, a <picture>, or a wrapper (<figure>) holding at most one of them. The chrome's content render rewrites only src, srcset, alt, width/height and the <source> list, and fires cms:change as today. Anything else is the host's, via cms:change.

5 · MediaStore reshape (Breaking)

5.1 · Today

// src/types.ts
export const MediaVariantSchema = z.object({
  width: z.number().int().positive(),
  format: z.enum(["avif", "webp", "png", "mp4"]),
  url: z.string(),
});
export interface MediaStore {
  upload(file: Uint8Array, meta: { role: string; filename: string; alt: string }): Promise<{ id: string }>;
  resolve(id: string): Promise<MediaVariant[] | null>;
}
  • The whole file sits in memory, and the answer waits for processing (minutes for a 60 MB loop in portfolio).
  • The variant shape is fixed: no height, crop or poster. South of the River's { w, key } and portfolio's crop: "fold" both have to squeeze into it.
  • alt is upload metadata, so one image can't carry different alt text on two pages, and it is never drafted or revisioned.
  • role is a free string the host has to pass in; the store doesn't know which field the upload is for.
  • Nothing in the package calls it, and it has no contract tests.

5.2 · Streaming upload

A · ReadableStream body Recommended

upload(body: ReadableStream<Uint8Array>, file, field, context). The handler passes request.body through a byte counter that errors the stream past the limit or the declared size, so a lying Content-Length can't overrun. Web standard: works in Node, Bun, Deno and workers. The store can spool to disk (portfolio), pipe to S3, or buffer if it likes.

B · Pass the Request

Simplest for the handler, but ties the store to HTTP, and every store re-parses headers and limits. No.

C · Keep Uint8Array, cap it

No reshape, but a 60 MB loop is 60 MB of heap per upload. Fails the issue's goal.

D · Direct to storage (signed URL), later

An optional direct?(field, file) returning { url, method, headers, token }; the browser uploads straight to S3 or Supabase, then POST media-complete { token }. Needed on hosts with a request-body cap (serverless: Vercel's is 4.5 MB). Designed in, not built in v1 (question 8).

Browser side, whatever the option: the widget sends the File itself as the body of an XMLHttpRequest, which streams it from disk and is the only API with upload progress in all three engines. Fetch upload streaming is Chromium-only and has no progress. No chunked or resumable upload: an interrupted upload restarts from zero (known limit).

5.3 · 202, the job and the poll

upload answers { status: "ready", media } (handler: 201) or { status: "processing", job, retryAfterMs? } (handler: 202). A store that processes synchronously never needs job. The widget polls GET media-job, which calls store.job(jobId, field).

Failure policy for polling (proposed, to be written into docs/chrome.md and tested)
Interval
First poll 1 s after the 202, then 2, 4, 8 s, then every 15 s (cap). A retryAfterMs from the store (or a Retry-After header) sets the next wait instead, clamped to 1 to 60 s.
Bound
One request in flight per job; at most one job per field (a new pick aborts the old one), so the page polls at most as many jobs as it has media fields. A job costs about 4 + 40 requests over its 10 minutes.
Give-up
10 minutes after the 202 (mountEditor({ media: { jobTimeoutMs } }), default 600 000), or 6 polls in a row that fail (network error, 5xx, an unreadable body).
Terminal at once
ready (commit, §6.5), failed (error with Retry), 404 (gone: mediaJobGone), 403 (access lost: notEditable).
What resets
A readable processing answer sets the failure count back to 0; it does not move the deadline or the backoff. Keep waiting starts over: new 10-minute deadline, failure count 0, next wait 1 s. A tab coming back from hidden polls once straight away and changes nothing else. Nothing else resets.
What the editor sees on give-up
Nothing is written. The field keeps its value, gets the failed outline, and an error toast says mediaJobSlow with Keep waiting and Cancel upload, announced once. The popover shows the same with Choose another file. The job may still finish on the server; if it does and nobody keeps waiting, its media is unreferenced and left for the host's garbage collection.
Stops polling
Any terminal state, give-up, Cancel upload, Esc, Done → Stop and finish, destroy(), Discard or Restore on the field's document, and page unload. Each one aborts the request in flight.
The send itself
No overall timeout (large files take as long as they take). Stalled: no progress event for 60 s aborts it as a network error. 503 with Retry-After: sent again after it (1 to 60 s), at most 3 times, then an error with Retry. No other automatic retry.

5.4 · Host-defined variants: how the widget gets a preview

A · Keep a fixed variant list

Hosts map their variants to { width, format, url } and the chrome builds srcset. Loses height, crop, poster; every host maps.

B · Opaque variants + a standard render Recommended

MediaStore<V>: resolve returns the host's own variants: V, which the package never reads and never sends, plus render in HTML's own vocabulary: src, srcset, sources: [{ type, srcset }], width, height, poster. The host builds it from its variants once, in its store; the chrome applies it without knowing what a variant is; the host's pages can use the same function.

C · A preview URL only

preview: url. Enough for the popover, but the host image after a change would show one fixed size and the chrome couldn't fill a <picture>.

5.5 · The interface, recommended

// src/types.ts (core, zod allowed)
export interface MediaFieldRef { key: string; path: string }  // the field the upload is for

export interface MediaRender {               // all the chrome reads; also the wire shape (wire-types.ts)
  kind: "image" | "video";
  src: string;                               // a URL the browser can show at once: preview and <img src>
  srcset?: string;                           // for <img srcset>
  sources?: { type: string; srcset: string }[]; // for <picture><source type>, best first
  width: number; height: number;             // intrinsic size, for width/height and the aspect ratio
  poster?: string;                           // video
  filename?: string;                         // for the publish diff and the popover
}
export interface ResolvedMedia<V = unknown> { id: string; render: MediaRender; variants: V }

export type MediaUploadAnswer<V> =
  | { status: "ready"; media: ResolvedMedia<V> }
  | { status: "processing"; job: string; retryAfterMs?: number };

export type MediaJobState<V> =
  | { status: "processing"; progress?: number; retryAfterMs?: number }   // progress 0..1, optional
  | { status: "ready"; media: ResolvedMedia<V> }
  | { status: "failed"; reason: string; message?: string };

export class MediaRefusal extends Error {      // thrown by accept/upload; mapped to a status by the handler
  constructor(readonly code: "too_large" | "unsupported" | "invalid" | "busy",
              message: string, readonly detail?: { limit?: number; retryAfterMs?: number }) { super(message) }
}

export interface MediaStore<V = unknown> {
  /** Before the body is read: refuse early on type or declared size. Optional. */
  accept?(field: MediaFieldRef, file: MediaFileInfo, context: WriteContext): Promise<void> | void;
  upload(body: ReadableStream<Uint8Array>, file: MediaFileInfo, field: MediaFieldRef,
         context: WriteContext & { signal: AbortSignal }): Promise<MediaUploadAnswer<V>>;
  /** Required when upload can answer "processing". null: unknown job, or not this field's. */
  job?(job: string, field: MediaFieldRef): Promise<MediaJobState<V> | null>;
  cancelJob?(job: string, field: MediaFieldRef): Promise<void>;
  /** Batched. A missing id is left out of the map. */
  resolve(ids: readonly string[]): Promise<Map<string, ResolvedMedia<V>>>;
}
export interface MediaFileInfo { filename: string; type: string; size: number | null }
  • MediaVariantSchema and MediaVariant go (Breaking). role goes: the store reads the field and picks its own.
  • runMediaStoreContract joins @yl/editor/contract: limits, a job that belongs to another field reads null, resolve leaves unknown ids out, an aborted signal stores nothing.
  • A small in-memory test store in examples/demo/ proves it in the real-browser harness, with a switch for "answer 202" (the issue's done-when).

5.6 · The wire

A · An option on createContentHandlers Recommended

createContentHandlers({ …, media: mediaStore }). Same base, CSRF and same-origin guard, locals, access and error envelope. The routes exist only with the option, like publishDue; without it they are 404.

B · A separate createMediaHandlers

Its own base (/api/media), but it repeats the guard and still needs the content store to gate by document.

Method Path Body Success Verdict
POST {base}/media?key=k&path=p The raw file. Content-Type its type, Content-Length, X-Upload-Filename (URI-encoded) 201 { media: { id, render } } or 202 { job, retryAfterMs? } canEdit on the stored row of k
GET {base}/media-job?key=k&path=p&job=j none 200 { status: "processing", progress?, retryAfterMs? } · { status: "ready", media } · { status: "failed", reason, message? }; unknown job 404 canEdit on k
DELETE {base}/media-job?key&path&job none 204; 405 when the store has no cancelJob canEdit on k
GET {base}/media?key=k&ids=a,b none 200 { media: { [id]: render } }, unknown ids left out, at most 100 canEdit on k
  • New error codes: too_large 413, unsupported 415, busy 503 (with Retry-After). invalid maps to the existing bad_request. A refusal from accept answers before the body is read.
  • Gated by the document the field is in, not by a separate media permission: who may edit the page may put an image in it. The path is passed to the store, not checked against the schema (the field write that follows is). A media id is not secret: the gate is on uploading and on job state, and GET media asks for a key so the same verdict applies.
  • onChange is not fired for uploads: nothing in content changed. The field write that follows fires field as usual.
  • Client: client.uploadMedia(field, file, { onProgress, signal }) (XHR), client.mediaJob(field, job), client.cancelMediaJob(field, job), client.media(key, ids). Types live in wire-types.ts as plain TypeScript, hand-checked like the existing error envelope: no zod in client.ts, wire-types.ts or the chrome. The zod request schemas go in wire.ts.

5.7 · The stored field value

A · The id alone

"m_9f2c…". Alt text would be a second field, or upload metadata (today). Easy to forget.

B · { id, alt, decorative? } Recommended

{ id: "m_9f2c", alt: "Cardamom buns cooling on a rack" }, or { id, alt: "", decorative: true }, or null for no image. Alt text is per use, drafted, published, diffed and revisioned. decorative tells "chose no alt text" from "hasn't written it". Exported schema: mediaValue() from @yl/editor (zod; refuses decorative with a non-empty alt).

C · { id, alt: string | null }

null = not written, "" = decorative. Shorter, but a host that renders alt={value.alt} drops the attribute for null, and the diff can't say "decorative".

The value never holds URLs or variants: those can change (a re-encode, a CDN move) without a content write. The host's page renderer resolves the id, as it does today.

6 · Host contract

  1. 1 · What decides what the chrome dresses The markup, as for every field: data-edit-field with data-edit-type="media", from field(path, "media", { label, accept?, maxBytes? }). accept (a list of MIME types, as for <input accept>) and maxBytes become data-edit-accept and data-edit-max-bytes; both are hints for an early refusal, the server decides. What the content render targets is decided at scan, attach, swap and refresh from the element, never from layout:
    • the element itself when it is an <img>, <picture> or <video>;
    • else its one descendant of those kinds (a <figure> wrapper, say), or none when it holds none (an empty wrapper);
    • more than one, or any other element with a background-image look: no content render, a warning, and cms:change only.
    Recommended markup: a wrapper for a field that may be empty, the <img> itself for one that never is. A caption is its own text field, grouped with data-edit-group on the figure.
  2. 2 · What the chrome adds to host markup, and how it is given back While editing, on the field element only: the existing cms-field and state classes, tabindex, aria-describedby, data-cms-state, plus cms-field--drop during a drag and data-cms-empty on an empty wrapper. Badges, the veil, the popover and toasts live in body. Done and destroy() remove all of it, including a class attribute the host never had, whichever part lets go first, through the existing restore path. The content render is the only write that stays, as for text: on the target it sets src, srcset (or removes it when render has none), alt, and width/height only when the host's element already had them; it never touches sizes, class, loading, decoding or anything else. In a <picture> it replaces the <source> elements with one per render.sources entry, keeping the first old source's sizes. In an empty wrapper it inserts one <img> (or <picture> when there are sources) as the only child, so a host :empty rule stops matching and > img:first-child starts. When the value goes (Remove, or Discard to none) a wrapper is emptied of the element the render targets; an <img> field can't be emptied and keeps showing, with cms:change carrying undefined. cms:change fires after every content render with detail: { key, path, value, render }; Recommended also cancelable: a host that calls preventDefault() renders it itself and the chrome writes nothing.
  3. 3 · Host CSS it can't support
    • Supported unchanged: object-fit, object-position, aspect-ratio on the image or its wrapper, sizes, lazy loading, a <picture> with type-switched sources.
    • Art-directed <picture> (<source media> with different crops): the content render can't reproduce it, because render has no media queries. While editing the new image shows one crop at every width. Warned; the host renders it from cms:change.
    • CSS background-image fields: not supported by the content render (a CSP-safe custom property would need host CSS written for it). Warned; cms:change only.
    • An <img> field can't show an empty state (replaced elements draw no ::before), and a wrapper clipped to zero height has no box to click or drop on: give an empty wrapper a size, or let data-cms-empty's min-block-size stand.
    • A new image with another aspect ratio shifts layout while editing unless the host fixes the ratio.
    • An ancestor with overflow: hidden clips the outline, as for every field.
  4. 4 · Lists, groups and plain fields
    • Plain field: as above.
    • In a list item (itemFields, keyed): a cell like any field. An upload belongs to the field's address (artists[_key=a1].photo), not to its element, so it survives a move, a swap or a refresh. Add with newItem that has no media renders the new item's media field empty (wrapper) or keeps the cloned image with the empty value (an <img> field, the same limit as above). Duplicate copies { id, alt }: both items show the same media, nothing is copied in storage. Remove leaves the media in storage (host GC).
    • Positional addresses (artists.2.photo): the list keeps today's rule (no list chrome). An upload finishing after the list changed under it would write to another item, so it is held as a conflict instead (§6.5, catch-up).
    • In a group: one of the group's fields. The frame and lines go round the wrapper; nothing else changes.
    • Drag to reorder a list item and a file drag never mix: a file drag is told apart by dataTransfer.types containing Files.
  5. 5 · Lifecycle
    Event What happens to a media field and an upload or job in progress
    Edit Dressed at scan. No media request until a field is opened; then one GET media for the current value's preview, cached for the session. The page-wide file-drop guard goes on. A beforeunload prompt is registered only while an upload or job is in progress.
    Leaving the popover Ready and changed: commit. Uploading or processing: the popover closes, the field shows the veil, it goes on and commits when ready (through a new ctx.continueInBackground(task); bound: one task per field, a new pick aborts the old). Untouched: nothing.
    Esc / Cancel / Cancel upload Stops the send or the poll (and cancelJob if the store has it). Writes nothing.
    Done An open popover that is ready commits, as today. Anything uploading or processing: the Finish editing sheet (§2.6). Keep uploading stays in edit mode; Stop and finish aborts them, writes nothing, then Done as today. Content renders already made stay.
    destroy() No prompt. A ready popover value is committed (the rule for open widgets); every upload and poll is aborted and writes nothing; the veil, guard and beforeunload go.
    Discard Stops uploads and jobs for the document's fields first (the sheet names them: "The upload for Hero image will stop"), then repaints from the published value, resolving its ids with one GET media. Never published: the document is deleted, its fields stop being editable, wrappers are emptied, an <img> keeps showing until reload.
    Restore Stops that document's uploads (toast mediaStoppedBy), then repaints like Discard.
    Catch-up, Take theirs Repaint from their value. An upload still going for that document keeps going; when ready, it is held as a field conflict (Keep mine / Take theirs), never sent on the copy just taken: the rule for a widget left open through catch-up.
    List swap, refresh The upload follows the address. The veil re-attaches to the new element. If the address is gone when it becomes ready (its item removed), it is not written: mediaItemGone, failed outline nowhere, an error toast. The media stays in storage.
    A late finish After Done → Stop, destroy() or navigating away, the server's job may still finish. Nothing in the page listens any more: no write, no warning. The media is unreferenced (host GC). Navigating away while one is in progress gets the browser's own leave prompt.
    Locked field No popover, no drop target, no paste: each attempt shows notEditable. A document that loses edit access mid-upload: the 403 ends it as an error.
    Publish Commits an open ready popover first, as today. Uploads in progress are not changes: the sheet notes them (mediaPublishPending) and publishes what is saved. Missing alt text is a note (mediaPublishNoAlt).
  6. 6 · Console warnings (all console.warn, once per field per mount, re-checked on refresh and swap, like the group warnings)
    • A media field whose element is not an image, picture, video or a wrapper of at most one: "…gets no content render; listen for cms:change".
    • A <picture> with <source media>: art direction isn't kept while editing.
    • A <video> target when the media for it answers kind: "image", or the reverse (once per field per value).
    • The server answered a render with no src, or an unreadable media body: once per mount.
    • Not warned: a give-up, a refusal, a late finish, a missing alt (those are the editor's, shown on screen).
  7. 7 · Known limits
    • No resumable upload: a dropped connection restarts from zero.
    • Hosts with a request-body cap (serverless) need the direct-to-storage path (5.2 D), not in v1.
    • Unreferenced media (cancelled late, given up, removed items, replaced images) is the host's to collect. The package never deletes media.
    • The local preview needs img-src blob: in the host CSP; without it, and for HEIC, the plain tile shows until the server's preview.
    • No media library: picking an existing image is a host panel (question 12).
    • No crop, focal point or rotation in v1.
    • One file per field: no multi-file drop into a list (a drop of several takes the first, and says so).
    • After Done the page shows the render, not the host's own markup, until it re-renders or reloads (onExit: () => location.reload() fixes that).
    • Chrome tests run in happy-dom; drag and drop, paste and XHR progress need the Playwright specs on three engines.

8.2 · Rulings on the review's questions

  1. If the last upload finishes while the Finish editing sheet is open, Done completes by itself.
  2. Removing a list item stops its upload or job, and the Remove toast counts it as a dropped change (removedDroppedToast).
  3. cms:change is cancelable for media fields only: it is dispatched before the write, and the write happens only if no listener called preventDefault(). Text and rich text keep today's order.
  4. A field that is the <img> or <picture> itself has no Remove button. A wrapper is documented for optional images.
  5. The preview of the current value is the target's currentSrc, with no request. An id the store no longer resolves shows mediaMissing (§8.1).
  6. The "No alt text" chip shows only for values this session has loaded. The Publish sheet note covers the rest.
  7. Paste onto a focused field or button is checked in e2e on WebKit. If WebKit doesn't fire it, it becomes a documented known limit.
  8. New copy: mediaRefused, mediaServerError, mediaMissing (§8.1).
  9. The stall timer starts at the first upload progress event. There is no cap on concurrent uploads.
  10. Drop, paste, the veil and data-cms-empty belong to the default widget in v1. ctx.continueInBackground is public on WidgetContext, so host widgets can use it.

8.3 · Widget contract and background tasks

  • ctx.continueInBackground(task): task is { done: Promise<value>; abort(): void }. Calling it settles the context like commit/cancel. The chrome keeps tasks in a registry keyed by slot id (key:path), never by field record, because a scan makes new records. When done resolves, it runs the same path as commit: the changed check against the initial value, then a held conflict if the slot is marked theirs, else session.save. The take step marks every task of the key with no queued or sent save, as it marks the active widget. A reopened widget gets the running task (ctx.background) and shows its state. One task per slot; a new pick aborts the old.
  • A task commits on ready only if no popover is open or opening on its slot. Otherwise the popover takes the ready state (the §3 focus rule) and commits on Done or leave. A popover always mounts from the slot's task when there is one.
  • handle.commit() means leave, on every path that calls it (opening another field, opening a sheet, Done, a list write, a rescan, refresh, Restore, destroy()): ready → commit; uploading or processing → continue in the background; failed or given up → keep the task; untouched → nothing. The Finish sheet opens before Done tears down the open widget. destroy() aborts after the commit.
  • Upload state never touches SaveSlot. One function derives what a field shows from the slot state and the task state, with this precedence: save failed or conflict → upload failed or given up → uploading or processing → saving → saved → idle. Every place that writes field state goes through it. ctx.unsaved stays about the save queue only.
  • Finish sheet: Esc or Close means Keep uploading. onExit waits for Stop and finish. Done drops failed and given-up tasks and hides their toasts, so nothing starts uploading while not editing.
  • One invariant for stale answers: each task has an epoch. Every abort cause bumps it (Esc, Cancel upload, a new pick, Discard or Restore success, Stop and finish, destroy(), access lost, document gone, item removed). Every continuation checks it before touching state, DOM or the queue: XHR load, a poll answer, .json(), the Retry-After wait, GET media. cancelJob is fire-and-forget.

8.4 · Save queue, Discard, Restore, Publish

  • When Discard or Restore starts on a document, its tasks freeze: a ready answer is held, not committed. On success they are dropped (abort and cancelJob). On failure or conflict they unfreeze, and a held ready goes through the theirs rule. This lives inside discard() and restoreRevision(), so a host panel calling api.discard gets it too.
  • While the Publish sheet is open, a background commit re-runs that document's review, and Confirm waits for it as it waits for writesSettled. The sheet never publishes a diff it didn't show. A document whose only change is an upload in progress still gets its mediaPublishPending note, including in the "Nothing to publish" state.
  • At ready, the address is resolved against the session's payload. Gone → mediaItemGone. Present and marked theirs → held. A path error on a media save maps to mediaItemGone, never to a generic failure toast whose Retry can't succeed.
  • Toasts: background info and saved messages follow provideStatus's rule (while an error toast shows, only announce). mediaSavedLater replaces the generic Saved toast for that slot. mediaStoppedBy is folded into the Discard or Restore toast. A background error never replaces an error toast with actions; the outline and the popover keep it recoverable.

8.5 · Lists, swaps, refresh, groups

  • Target detection and "empty" ignore .cms-root descendants (the list toolbar and band). A render into an empty wrapper inserts before the first non-chrome child and never removes siblings. The > img:first-child claim in §6.2 doesn't hold under a list toolbar; the docs say so.
  • Recommended markup: <figure data-edit-group><div data-edit-field="hero" data-edit-type="media">…</div><figcaption data-edit-field="caption">. A group element that is itself a field is ignored, as today. Warn when an <img> or <picture> is a data-edit-item.
  • §6.4 correction: Add and Duplicate swap in the page's markup. Nothing is cloned, so an Add renders whatever the host renders for the new item.
  • The veil and the task follow the slot id, not the element. Both are re-bound in attach and rescan. Every connected copy of the field gets a veil; a disconnected or boxless element gets none. A host re-render on cms:change that replaces the element is picked up at the next rescan or refresh.

8.6 · Content render

  • A session cache of MediaRender by id, filled from ready answers and GET media. Uncached ids are batched per microtask into one GET media per document, at most 100 per request. Each record has a render ticket, so a late answer never overwrites a newer render. No render after destroy().
  • GET media failing or missing an id writes nothing and fires cms:change with render: null (undefined stays the value-is-null case).
  • An alt-only change (same id) writes only alt, because the host's own src may differ from render.src. Media bypasses the generic text write: an empty wrapper or an <img> never gets textContent = "". Blob preview URLs are revoked and never reach host markup.
  • The chrome reads values with a hand-checked reader (no zod). It accepts a bare id string (legacy) and { id } without alt. It never writes decorative: false and writes keys in the order { id, alt, decorative }. An unreadable value is treated like formWidget's unreadable: leaving untouched writes nothing.
  • A host that renders asynchronously after preventDefault() leaves the target and data-cms-empty as they were until the next attach. This is documented.

8.7 · Veil, empty state, drop, paste

  • The veil has pointer-events: none and aria-hidden. Its position is position: fixed in viewport coordinates, measured from the target's rendered box (not an inline field element's line box). It is re-measured by a ResizeObserver plus capture-phase scroll and resize, batched in rAF.
  • data-cms-empty is set in attach and restored in the same detach closure. It toggles after every render that empties or fills the wrapper, and after a cancelled cms:change. Groups, lists and outlines re-measure after it toggles. cms-field--drop joins the host-class restore list. The aria description says empty, uploading, failed or missing alt.
  • Drop guard: installed only while editing, and only when at least one media field is dressed. It acts on file drags only, in the window's bubble phase, and only when the event isn't already defaultPrevented, so host drop zones and file inputs keep working. Outside media fields it sets dropEffect = "none". A drop on a locked field shows notEditable; inside a busy list, listBusy. Drag enter and leave are counted, so child elements don't flicker the class. The badge is driven by drag events. dragstart is cancelled inside dressed media fields, so dragging image A onto field B never uploads a copy. A drop on a field with a running task replaces it.
  • Paste: a mixed clipboard (text and image) pasted into Alt text pastes the text. A paste on a locked field or into a busy list follows the drop rules.

8.8 · Wire and HTTP

  • The router takes several methods per route name (media: GET and POST; media-job: GET and DELETE), with the right Allow header. A store without cancelJob answers 204 to DELETE (nothing to cancel), not 405.
  • An unknown job gets its own error code, job_not_found, distinct from a missing document's not_found. A missing document marks the field's document as unknown. An unknown route (the media option is off) logs one console.warn for the developer.
  • errorResponse can set headers: busy carries Retry-After. The client maps a 413, 415 or 503 without our envelope (a proxy's HTML) by status.
  • An early 413 or refusal is verified on three engines against the demo server. If the browser loses the status, the handler drains and discards the body up to a cap before answering.
  • The option is media: { store, maxBytes }. The handler checks the declared length and counts the bytes; with no length, size: null and the counter enforces.
  • variants never leave the server (a handler test proves it). MediaRender gets a compile-time Same<> guard between core and wire types. The client hand-checks bodies: src is a string, width and height are positive, progress is clamped to 0..1. GET media takes repeated id= params, not a comma list. X-Upload-Filename decoding can't throw (a bad one becomes bad_request). Filename and type are untrusted, and the docs and the contract say so (path separators, SVG). ContentClientOptions takes an injectable XHR for tests.
  • Contract suite: upload rejects when the body stream errors; a job stays readable for a while after ready; options are a factory, sample bytes, whether the store processes asynchronously, and its limit.

8.9 · Upload and poll policy additions

  • The stall timer runs only between the first upload progress event and the upload's load. A store that processes synchronously and answers late is never killed by it.
  • Give-up happens only after a poll answer: when the deadline passes, poll once more. Never give up while the tab is hidden. The poll on becoming visible doesn't add a second request while one is in flight, and doesn't fire during a 503 wait or after give-up.
  • While navigator.onLine is false, no poll is sent, so nothing counts as a failure; on online, poll at once.
  • Retry-After (seconds or an HTTP date) wins over retryAfterMs, clamped 1–60 s. A 503 on a poll counts as a failure, and its Retry-After sets the next wait. The 3 automatic resends count per task; Retry resets them. Esc cancels the countdown; leaving keeps it going in the background.
  • When refresh() finds a document no longer editable or no longer returned, its tasks are aborted at once. A failed load that locks every field aborts nothing. On pageshow from the back/forward cache, a task that was sending fails with Retry.

8.10 · Accessibility

  • Before a state change removes the focused control, focus moves to the new state's control: Retry, Keep waiting or Choose file. This keeps focus from falling to body, which the popover would read as leaving. Done before ready is aria-disabled, not disabled.
  • Progress steps are announced only for the task whose popover is open, once per step per task, not per resend. Background tasks announce only terminal events. Two announcements in one tick are joined, not overwritten. The Finish sheet's percentages are not live. Space opens a media field (Enter already does), with preventDefault.

8.11 · Diff and formatting

  • A media value diffs as one entry under the field's path (keyed list paths are mapped to the diff's index paths): "new.jpg (was old.jpg)" from a batched GET media, falling back to ids when the publisher gets a 403. An alt-only change shows as alt. Missing-alt notes cover media fields on this page only.
  • Sizes are formatted as kB, MB or GB, in 1000s, matching the server's maxBytes. A file at the limit is not refused. accept matching takes image/*, extensions such as .heic, and is case-insensitive. An empty file type is never refused in the browser: the server decides.

8.12 · Real-browser checks (e2e, three engines)
