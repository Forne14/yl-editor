Editing lists in place

Issue #28. Today the chrome edits one field at a time. A site can't add a gig, remove an artist or reorder a roster. This page proposes the chrome for keyed lists (items[_key=abc]). Every demo below is live: click, tap, hover or tab through it. The look is the chrome's own (--cms-* tokens copied from src/chrome/chrome.css); the host page is a neutral stand-in. Phone frames are 390px and mimic a touch device (tools collapse to a chip); desktop frames mimic a pointer device. Frames narrower than 40em use the chrome's bottom-sheet layout, the same breakpoint as chrome.css.

Yassine's constraint (2026-11-11), before any decision below

No overlapping dashed outlines. Closely placed elements are grouped inside one larger dashed outline, with a single dashed separator between them.

This revision follows it (D1). A list is one dashed outline. A single dashed line separates each item from the next, and each field from the next inside an item, so the list reads as a grid. Every line stops where it meets another, and nothing nests or crosses. Hover, editing and keyboard focus are solid and drawn inside a cell, so they never touch a dashed line. The list's tag and each item's toolbar sit on a line, like a fieldset legend, not in a box of their own.

Status: revised 2026-11-14 for the constraint. Waiting on Yassine for D1–D9. Nothing is built yet.

Decisions for Yassine

Each has a recommendation. The demos below show it, and the alternative where it is a close call.

  1. How is a list marked in edit mode? Recommend A, the grid

    A, the grid: one accent dashed outline round the list (the fields' own outline token). Thin dashed lines separate the items and the fields inside each item. Fields in a list have no outline of their own. The tag “Artists · 3 of 6” sits on the top edge. B, rows only: the same outline and item lines, but no lines between fields. A field shows itself only on hover or focus (demo 1, last frame).

    A keeps the at-rest promise every other field makes: you can see what is editable without hovering, which matters on touch where there is no hover. B is calmer and cheaper to build, because the item lines are pure CSS. A's field lines are placed from the fields' boxes (custom properties, CSP-safe) and redrawn on resize. On a phone, B hides which parts of an item can be edited.

  2. Where do an item's controls live? Recommend floating toolbar

    A toolbar that sits on the item's top line at the right, centred on it, the way the tag sits on the outline (outside the content, skinmenu's pattern). Pointer: shown on hover and on focus inside the item, which also tints the item's band. Touch: a 44px chip in the same place on every item; tap it to open the toolbar. Keyboard: one tab stop per item (a role="toolbar"), arrow keys move between its buttons.

    Controls inside the item would restyle host markup. A toolbar per item as 5 tab stops would add 5 stops per item; a roving toolbar adds 1.

  3. Reordering. Recommend drag handle + buttons

    Drag handle for pointer users, always with Move up / Move down buttons as the single-pointer alternative (WCAG 2.5.7 Dragging Movements). Arrow Up/Down on the focused handle also moves. Lists whose order follows the data (events by date) show neither handle nor move buttons.

  4. Remove: undo toast or confirm? Recommend undo toast

    Both are shown in demo 4. The undo toast removes at once, keeps the last removals undoable (button, or Ctrl/Cmd+Z in the list), and stays 15 seconds.

    A removal is only a draft change: nothing is public until Publish, and revisions keep the published version. A confirm on every remove trains people to click through it and costs a step each time.

  5. Add: where, and what opens? Recommend one Add, at the end

    One Add button under the last item, in both the empty and the populated state (skinmenu rule 14). A new item appears at the end and its first field opens for typing. Duplicate puts the copy right after the original. In a date-sorted list the new event sits at the end until its date is saved, then moves to its place and the move is announced.

    No “insert here” between items: Duplicate and Move already cover it, and it is a lot of extra targets on a phone.

  6. Limits. Recommend aria-disabled + visible reason

    At max, Add (and Duplicate) stay focusable but inert with aria-disabled, and the reason is on screen and tied to the button. At min the same for Remove. A natively disabled button drops out of the tab order and can't explain itself.

  7. Duplicate is opt-in per list. Recommend default off

    The roster has none (a second “Mara Okoye” is never wanted); events have it (a repeat gig). Show/hide on an item (SOTR's visible) is an ordinary toggle field inside the item, not list chrome.

  8. How does a new item's markup reach the page? needs your call

    The chrome can insert the data (existing ArrayOp insert) but not the host's HTML. (a) The chrome re-fetches the page and swaps the data-edit-list element. (b) The host passes a render(item) callback. I lean (a): SOTR is server-rendered and has no client template, and (b) would duplicate the markup. Detail in the notes.

  9. The same rule outside lists? needs your call

    Plain fields placed close together (a heading over its subtitle) still get one outline each today, and those outlines can cross. The rule as written covers them too. Grouping them takes the same line painter, plus a way to say which fields form a group. I'd make that a ticket of its own after #28 and leave existing fields alone here.

  10. Lists laid out in a row or a grid. needs your call

    Every demo here is a column. Portfolio's hero slides and project grid run sideways. Proposal: the chrome reads the axis from the items' boxes. In a row the item lines are vertical and the toolbar sits on the item's left line at the top. A wrapping grid gets both, still one outline. That isn't drawn here yet; say if you want it in the prototype before approving.

1. Edit mode at rest

One dashed outline per list, with its tag on the top edge. A thin dashed line between items and between the fields inside an item. Fields in a list have no outline of their own. On the phone each item has a small “⋯ n of N” chip on its top line (the only way in without hover). The Add button is the last row, under the last line. Last frame: alternative B, rows only, with no lines between fields.

2. An item's controls

Hover or tab into any item on desktop; tap a chip on the phone. The item's band tints, and the toolbar sits on its top line. The toolbar is Drag handle · Move up · Move down · Duplicate · Remove, each 44px. Tab enters the toolbar once; Left/Right/Home/End move inside it; Tab again goes on to the item's fields. The first item's Move up and the last item's Move down are inert (aria-disabled) and say why on activation. Item 2 is pinned open in the stills.

3. Add

Add is present when the list is empty and when it has items. Pressing it puts the new item last, opens its first field with the caret in it, and moves focus there. Edit the field and press Enter, or Escape to keep the default. For an event the first field is the date; saving it moves the event into date order.

4. Remove: undo toast (recommended) and confirm

Undo: the item goes at once, focus moves to the item that took its place, the toast offers Undo. The toast sits in the DOM straight after the list, so Tab from the list reaches Undo, and Ctrl/Cmd+Z works while focus is in the list. Confirm: a popover (a bottom sheet on the phone) with Cancel and Remove; focus starts on Cancel.

5. At the maximum (and minimum)

This roster allows 6 and holds 6. Add is inert and says “Maximum of 6 artists. Remove one to add another.” The tag reads “6 of 6”. Remove one and Add comes back. A list may also set a minimum: the last frame holds the minimum (1 artist) and Remove is inert with its reason.

6. Focus after each operation, and what is announced

The announcements go to one polite live region (role="status") that the chrome already owns. Each demo frame above prints what it announced under it, newest first; use a screen reader to confirm the real thing. “{item}” is the item's label: the value of the field named by data-edit-item-label, else “{noun} {position}”.

Notes: proposed public surface

A proposal for review, no code yet. Per CLAUDE.md the attributes, the mountEditor option and the defaultStrings keys are public API, so they are listed in full.

Attributes a host emits

Only for signed-in editors, like data-edit-field. Likely through editable() (edit.list(...), edit.item(...)) so hosts never hand-write them. 

<ul data-edit-list="artist/list:artists"
    data-edit-list-label="Artists"
    data-edit-list-noun="artist"
    data-edit-list-min="1" data-edit-list-max="6"
    data-edit-list-order="manual"        <!-- or "data": no handle, no move buttons -->
    data-edit-list-duplicate>             <!-- present = Duplicate on -->
  <li data-edit-item="artist/list:artists[_key=a1b2]"   <!-- itemPath(base, item, index) -->
      data-edit-item-label="name">      <!-- field name whose value labels the item -->
    <img data-edit-field="artist/list:artists[_key=a1b2].photo" data-edit-type="image">
    <h3 data-edit-field="artist/list:artists[_key=a1b2].name" data-edit-type="text">…</h3>
  </li>
</ul>
  • data-edit-list is "<docKey>:<path>", the same grammar as data-edit-field. Its children are the items.
  • data-edit-item is the full address of the item, built with itemPath so it uses [_key=…] when the item has a _key and an index otherwise. Index items work but can drift under concurrent edits, as paths.md already says.
  • Absent attributes mean: min 0, no max, order="manual", no Duplicate. label and noun default to the path's last name, singularised by the host if it wants better.
  • Chrome operations use the existing ArrayOps (insert, move, remove) on the list path. A stale list surfaces as the existing conflict toast (actionConflict).
  • The list and item elements get .cms-listedit and .cms-item (like .cms-field). The chrome adds its own, all .cms-root and aria-hidden except the toolbar: .cms-listedit__frame (the one outline), .cms-listedit__tag, and in each item .cms-item__tools, .cms-item__band (the line above it and the hover tint) and .cms-item__sep (the lines between fields). The lines between fields are placed from the fields' boxes through --cms-sep-* custom properties and redrawn when the list resizes or a field's text changes. The token block in chrome.css gains the two host selectors and four tokens: --cms-list-gap, --cms-list-pad, --cms-list-line, --cms-list-tint.

A new item's default, and its markup

mountEditor({
  lists: {
    "artist/list:artists": {
      newItem: () => ({ name: "New artist", line: "", visible: true }),  // _key added by the chrome if missing
      focusField: "name",                       // default: the first data-edit-field inside the new item
    },
    "event/list:events": {
      newItem: () => ({ title: "New event", date: null, venue: "" }),
    },
  },
});
  • Keyed by the list's docKey:path. Without an entry the list can't Add (the button is not shown) but can still reorder and remove.
  • _key: the chrome generates a short id when newItem returns none (decision for review: paths.md today says the host owns _key; this is the one place the chrome creates items).
  • Markup (D8): (a) lean: after the op is saved, the chrome re-fetches the page and replaces the [data-edit-list] element, then focuses the new item's first field. (b) option: render(item, index) => HTMLElement in the same entry for hosts with a client template.

Other things this implies

  • Docs: docs/chrome.md (attributes, option, keyboard) and docs/paths.md (_key creation). CHANGELOG under Unreleased.
  • Real-browser e2e on the demo site, because happy-dom can't prove hover, focus-within or pointer drag: keyboard-only add/move/remove/undo, touch chip, and an axe pass on the toolbar.

  • Reduced motion: the only new transition is the toolbar's 120ms opacity fade, which is already within the chrome's reduced-motion allowance.
