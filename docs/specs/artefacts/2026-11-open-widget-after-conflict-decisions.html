Three decisions behind #48

PR #50 (one hold for a field left open through a conflict) implements your ruling C: a field left open while another editor's change arrives is held as a conflict, with Keep mine / Take theirs. Two review rounds then found the same kind of bug, in the same place. The bugs come from three questions the ruling didn't settle. No new copy and no visual change in any option: they all use the conflict toast you approved.

1. How does the chrome know the other editor changed this field?

Ruling C holds only when their version changed the open field. To tell, the chrome compares their value with the value it had before. Often it doesn't have that value: a text field opens straight from the page's text, and the document itself is only fetched for popovers. So today the chrome guesses from the page (the visible text, or data-edit-value). Each review round found a page where the guess is wrong: a number in the attribute but a string stored, an icon inside the heading, rich text the site renders differently. Each wrong guess shows Amira “Someone else changed this field” when nobody did.

A · Fetch the stored value whenever a field opens recommended

The field still opens at once from the page's text. In the background the chrome fetches the document once (it already does for popovers, and caches it for the session). The comparison then uses the stored value, never the page. No guessing code.

Editor: a conflict toast only when the field really changed. Site developer: nothing new. One extra request per document on the first edit.

B · Hold whenever a conflict arrives under an open field

Don't compare at all. Any conflict on the document holds the open field, even if Ben changed a different field.

Editor: sometimes told “Someone else changed this field” when Ben changed another one. Simplest code.

C · Keep guessing from the page

What the PR does now. Every site's markup is a new way to get it wrong.

Editor: false conflicts on some sites. Not recommended.

2. A save that already failed, when their change to that field arrives

Amira's save of the title failed (network error), so it shows Retry. Then Ben's new title arrives through a conflict. Today Retry, or reopening and leaving the field, sends her title on Ben's version and overwrites his unseen. This was here before #48; review round 2 found the open-field form of it.

A · It becomes a conflict recommended

The Retry toast is replaced by the conflict toast: Keep mine (overwrite) / Take theirs (reload field). Same rule as an open field, so one rule covers both.

B · Leave it as a failed save

Retry overwrites Ben's change. Ruled out by #48's own aim, unless you see a reason to keep it.

3. The site closes the editor while a value is held

The site calls destroy() (a single-page site navigating away) while Amira's held value is waiting for Keep mine or Take theirs, or while the field is still open over Ben's change. The toast goes away with the chrome. Before #48 her value was saved over Ben's.

A · Drop it, as an unsaved field in a closed tab is recommended

Nothing is sent. Documented in docs/chrome.md. Ben's change stays. Amira loses her text, as she would by closing the tab.

B · Save it anyway

The behaviour before #48: Ben's change is overwritten and nobody is told.

C · Tell the site

A new event carries the held value so the site can keep it or warn. A new public surface to design and document; more than this ticket needs.
