List keys: who is responsible for them

Issue #28 (edit lists: add, remove and reorder keyed array items). Two recommendations of mine fell apart on a detail, which means there is a wider decision underneath: where an item's _key comes from, and who is responsible for it. This page explains why keys matter, the four places they could come from, and what each looks like in situ, for the editor and for the site's developer. Frames are stills of a desktop page in edit mode, in the chrome's own look.

1. Why a list needs keys

Every edit names what it changes by an address. Without a key, the only address an item has is its position: “the 3rd artist”. Positions change when an item is added, removed or moved, so an edit that is still waiting (it failed to save and will be retried, or it is queued) can land on whichever item has moved into that place. A key is a short id stored inside the item ({ _key: "i3", name: "Ines" }) that never changes, so the address “the artist with key i3” always names the same artist.

2. The decision: where do keys come from?

New items get a key from the chrome's Add, so the question is about content that already exists without keys. Something has to give those items keys. There are four candidates. Each needs one thing to be true, and that is where my earlier recommendations went wrong.

A · The editor, on the first change built now

The first Add, Remove or Move in a list writes a key into every item, then does what was pressed.

Needs: the page to show the items by key right after that write.

Breaks: the write is a change the editor didn't ask for. If the page still shows items by position, the press does nothing. Any unrelated validation error turns list editing off.

B · The schema, when content is read my first pick, unsafe

A schema helper adds a key to any item without one, every time the content passes through the schema.

Needs: what the schema adds to be saved.

Breaks: the store checks content against the schema on every read but saves nothing. Each page load invents new keys that aren't in the store, so edits to those items fail.

C · The store, when content is written

The store is told which lists are keyed, and any write to those documents adds and saves missing keys.

Needs: someone to save each document once before its lists can be edited.

Breaks: a list nobody has saved since the change shows no list buttons, next to lists that do. Every store a site brings has to do the same (a new rule in the contract suite).

D · The site's content recommended

The schema requires a key on every item (keyedItems), so the store refuses unkeyed items. Existing content gets its keys once, from a script (addListKeys) run at deploy or in a migration.

Needs: the site's developer to run the fill once per list when adopting.

Breaks: nothing at runtime. If the fill is skipped, that list shows the single outline with no list buttons, and the console says to run it.

3. What each looks like for the editor

A · The editor keys on the first change

The editor presses Remove on Tobias in a list whose items have no keys. The chrome writes keys into all three items (a draft change), asks the page again, and the page still renders the items by position. Nothing was removed, the toolbar has gone, and the bar counts a change the editor never made.

B · The schema keys on read

Two loads of the same page. Each load passes the content through the schema, which invents keys; neither set is saved. The editor opened the page at 10:02, a colleague's save made the chrome read again at 10:05, and the editor's next save goes to a key that no longer exists anywhere.

C · The store keys on write

The same site, two pages. The roster's document was saved after the change, so its items have keys. The events' document hasn't been saved since: its list has no buttons until somebody edits any field on that page and saves.

D · The site owns keys recommended

The editor never sees keys being made: every list has its buttons from the first load. The work is the site developer's, once, when adopting the editor. Shown here: the developer's two changes, and the one thing the editor would see if a fill were missed.

4. Side by side

A · editor, first change B · schema, on read C · store, on write D · site's content
Editor sees list buttons Yes, until a press fails Yes, but saves fail Only once the page was saved Always
Changes nobody asked for The keying write None saved Bundled into the next save None
Edits can land on another item No, once keyed Edits fail outright No No
Site developer's work None Add the helper Name the lists; custom stores implement it Add the helper; run the fill once
Code the editor carries Keying, moving pending edits, fallbacks None None None

Where the sites stand: South of the River already stores _key on its artists and events, so D costs it one schema change and no fill. Portfolio and skinmenu would run the fill once for each list they make editable.

5. What I'd like you to decide

  1. Where keys come from: A, B, C or D. I recommend D: the content owns its keys, the editor never invents them, and nothing surprising happens at runtime. It replaces ruling 3b (the editor keying on the first change).
  2. If D: does the store refuse unkeyed items? With keyedItems in the schema it would, so a script or another tool that writes items without keys fails loudly instead of creating unkeyed content. I recommend yes.
