Lists: five product decisions

Issue #28 (edit lists: add, remove and reorder keyed array items), PR #47 (the list fixes). Ten review rounds keep finding edge cases in list setups #28 never asked for. Each section below shows one decision in situ: on the left, what the chrome does today; on the right, the recommendation. The look is the chrome's own (--cms-* tokens, the approved grid outline from 2026-11-list-editing.html); the host sites are neutral stand-ins. Frames are stills of a desktop page in edit mode.

1. A list inside another list's item Recommend: top-level lists only

A menu with sections; each section has its own list of dishes. Today the inner list is a list too: its own outline, tag, toolbars and Add, inside a row of the outer grid. Keeping both in step needs a lock in both directions, and a write to one can bring back the other's older markup. Recommended: only the outer list gets list chrome. The dishes are still editable in place: they are fields of the section's row, separated by the same dashed lines. Adding or removing a dish is done by whatever the site offers for that (or not at all).

2. One list rendered twice on a page Recommend: the first one only

The same artists appear in the main list and again, lower down, in a shorter list (names only, different markup). Today both get list chrome, and an Add swaps the page's markup in by the list's address, so one copy can come back with the other's markup. Recommended: only the first copy on the page gets list chrome. The second keeps in-place editing of its fields (each field its own outline, as fields outside lists are today) and follows the first after every change.

3. A list the chrome can't edit safely Recommend: no list chrome, and a console warning

This site keys its items (artists[_key=a1]) but addresses their fields by position (artists.2.name). After a remove, a failed save at artists.2.name would be retried into whichever artist moved into place 2. Today the chrome shows the full list toolbar anyway. Recommended: the list keeps in-place field editing, gets no list chrome, and the browser console says why, for the site's developer. Editors never see the warning. The same applies when items aren't siblings, or a _key is missing; an invalid _key from newItem is replaced with a generated one instead.

4. Undo after another editor changed the list Recommend: the removal is dropped

Ines Duarte was removed. Before Undo, another editor reordered the roster and added Kofi Mensah. Undo hits the conflict: nothing is written and the page catches up to their version. Today the removal goes back on the stack and the Undo toast reappears, so a second press would insert Ines into their list at her old place. Recommended: the removal is dropped, the conflict toast says so, and the list's Undo button goes.

5. How long each removal can be undone Recommend: 15 seconds each

Two lists on one page, Artists and Events. The editor removes an artist at 0 s and an event at 10 s. Today one timer serves both: each removal restarts it, so the artist's Undo lasts until 25 s, and while an Undo is being written the other list's Ctrl/⌘+Z is ignored although its button still shows. Recommended: every removal has its own 15 seconds, and nothing pauses or extends another's. The stills show each list's Undo button and what Ctrl/⌘+Z does at four moments.
